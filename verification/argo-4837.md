# Recover a restored NGINX canary Ingress

| State | Before recovery | After documented recovery |
| --- | --- | --- |
| Canary Ingress controller UID | Stale source-cluster UID | Current destination Rollout UID |
| Argo Rollouts reconciliation | `TrafficRoutingError` for the canary Ingress | Controller creates a fresh canary Ingress |
| Stable Ingress | Original UID | Same UID |

The previous NGINX guide skipped cluster restores. The new section shows the two `kubectl` inspections, explains why the UIDs must match, and distinguishes the generated canary Ingress from the stable one during restore.

Both exact revisions passed `mkdocs build`. Only the candidate contains the restore section. The hosted job built the candidate controller with Go 1.26.11 and ran `go test ./rollout/trafficrouting/nginx`. It ran the controller against Kubernetes 1.37 in kind, simulated the stale owner reference through the real API, observed the reported error, and verified the documented lookup and recreation. The job simulated restored resource metadata and used no Velero installation or NGINX traffic.
