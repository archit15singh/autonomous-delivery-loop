# Autonomous delivery ecosystem

Research snapshot · 2026-11-20

The opportunity is to connect an approved outcome to trustworthy evidence from the exact code that ran. Keep Codex as the implementation agent, GitHub as the PR and CI system, and the existing delivery and telemetry systems as evidence producers. A small deterministic verifier and feedback policy can coordinate those pieces. That boundary is an architectural inference from the sources below.

## What the closest systems already do

- **Factory** describes a software-factory architecture spanning signals, planning, implementation, testing, shipping, and monitoring. That is the vendor’s stated direction. The announcement gives no independent comparison of how reliably it verifies a specific deployed business outcome. [Factory architecture announcement](https://factory.com/news/software-factory)
- **PostHog** documents a concrete signal-to-PR loop. It ingests GitHub CI data and uses deterministic queries to detect signals including flaky checks and performance regressions. An agent investigates the attached evidence and may open a fix PR. This supports using clear detectors to start repairs. It is a different measurement from proving a feature’s impact. [PostHog engineering report](https://posthog.com/blog/self-driving-ci)
- **OpenHands** documents event-triggered automations and ships an issue-to-PR template. These cover intake and execution if a dedicated orchestrator eventually proves necessary. The documented issue template establishes PR delivery. Post-deploy verification would still need a contract and evidence source. [OpenHands event sources](https://docs.openhands.dev/openhands/usage/agent-canvas/automation-events) · [Issue-to-PR automation](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/issue-to-pr)
- **GitHub Agentic Workflows** supports natural-language repository workflows on Actions, including Codex as an engine. Its documented guardrails include read-only tokens by default and declared safe outputs. Use ordinary deterministic Actions for the verifier. The agentic workflow is an optional entry point for triage or repairs. [GitHub Agentic Workflows](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows)
- **Stripe** reports an unattended coding-to-PR workflow whose outputs still receive human review. Its Minions combine deterministic steps with agent decisions. Stripe caps the workflow at two CI rounds to control cost and diminishing returns. That is useful precedent for an initial attempt plus one evidence-driven repair. [Stripe Minions implementation](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)

## Eight layers and the pilot boundary

| Layer | Source-backed capability | Codex-first decision |

| Coding | Codex offers non-interactive execution, JSON events, sandboxed writes, and resumable sessions. Claude Code and Devin are alternative implementation runtimes. [Codex](https://learn.chatgpt.com/docs/non-interactive-mode) · [Claude Code](https://code.claude.com/docs/en/overview) · [Devin](https://docs.devin.ai/get-started/devin-intro) | Reuse the existing Codex CLI, delivery skill, and preflight handoff. | Orchestration | GitHub Actions can run on PR, push and deployment events. Temporal persists event history for durable execution and is useful when work must resume over long waits or across systems. [GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) · [Temporal execution](https://docs.temporal.io/workflow-execution) | Use Actions and a small restartable controller first. Tie an attempt to a candidate commit and preserve the reason for every retry. |
| Verification | Playwright checks user-facing browser behavior. Checkly can reuse Playwright suites as deployed monitors. CodeRabbit provides PR review signals. [Playwright](https://playwright.dev/docs/best-practices) · [Checkly](https://github.com/checkly/playwright-check-suite-examples) · [CodeRabbit](https://docs.coderabbit.ai/) | Use the smallest meaningful probe for each contract. A real HTTP check is adequate for an API pilot. Add a browser flow when the outcome depends on the browser. Use reviewer output as supporting evidence. |
| CI and merge | GitHub supports branch checks and protected branches where the repository plan permits them. Mergify offers a queue for competing changes. Required checks are commit-specific, and GitHub can report a skipped job as successful. [GitHub protections](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [Required check behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) · [Mergify](https://docs.mergify.com/merge-queue/) | Require direct evidence that the designated checks ran for the current candidate. Recheck the head immediately before merge. Use the merge queue only if concurrent changes warrant one. |
| Deployment | Argo Rollouts can continue, pause or abort based on analysis. LaunchDarkly monitors flag variations and can roll back guarded rollouts. Harness integrates APM and log checks into deployment verification. [Argo](https://argo-rollouts.readthedocs.io/en/latest/features/analysis/) · [LaunchDarkly](https://launchdarkly.com/docs/home/releases/managing-guarded-rollouts) · [Harness](https://developer.harness.io/docs/continuous-delivery/verify/verify-deployments-with-the-verify-step/) | Measure the revision actually serving traffic. Start with a hosted staging exercise. Prefer an existing rollout control when production is authorized. |
| Runtime investigation | Sentry and Datadog document issue investigation using telemetry and linked source. Datadog explicitly allows an inconclusive investigation. [Sentry Seer](https://docs.sentry.io/product/ai-in-sentry/seer/) · [Datadog Bits Investigation](https://docs.datadoghq.com/bits_ai/bits_investigation/investigate_issues/) | Attach the relevant evidence to a repair task. Distinguish an application failure, transient infrastructure failure and missing evidence. Leave rollout authority with the release policy. |
| Outcome measurement | PostHog pairs variant assignment with exposure tracking and preselected metrics. LaunchDarkly guarded rollouts compare observed behavior against the original variation. [PostHog experiments](https://posthog.com/docs/experiments) · [PostHog experiment planning](https://posthog.com/docs/experiments/creating-an-experiment) · [LaunchDarkly rollout analysis](https://launchdarkly.com/docs/home/releases/managing-guarded-rollouts) | Define the impact metric, population, exposure, observation window and minimum sample in advance. | Scoring and learning | Braintrust, LangSmith and Phoenix package traces, datasets and comparative evaluations. [Braintrust](https://docs.braintrust.dev/evaluate) · [LangSmith](https://docs.langchain.com/langsmith/evaluation) · [Phoenix](https://arize.com/docs/phoenix/evaluation/llm-evals) · [Scale benchmark protocol](https://labs.scale.com/leaderboard/swe_bench_pro_public_v2) | Keep the deterministic grader outside the candidate’s edit authority. ## What the outcome contract needs to bind

1. **Implementation evidence.** Name the acceptance behavior, regression checks and expected source revision. Record independent check names, conclusions, run ID and attempt, workflow revision, PR number and head or tested merge SHA. Keep the expected identity distinct from the observed identity. Retrieve workflow results from the GitHub service, a protected judge, or another independently administered source. [GitHub workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28)
2. **Runtime evidence.** Bind the checked-out merge SHA to the built artifact’s digest, deployment identity and environment. Probe the live instance for its revision and contract behavior. Reject a mismatch even if the probe status is green. Record observed time and a way to retrieve the raw result. A digest establishes artifact identity. A signed attestation additionally depends on the builder, signer and verification policy. GitHub’s private-repository attestation feature requires Enterprise Cloud. [GitHub deployments API](https://docs.github.com/en/rest/deployments/deployments?apiVersion=2022-11-28) · [SLSA provenance](https://slsa.dev/spec/v1.2/build-provenance) · [GitHub attestation availability](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
3. **Impact evidence.** Record the target metric and threshold along with its source, cohort, observation window and sample count. Keep impact pending when the sample is too small, the attribution window is open, or there is no valid comparison. An observational association and a randomized treatment effect support different claims. [PostHog result analysis](https://posthog.com/docs/experiments/analyzing-results) · [Google SRE canarying](https://sre.google/workbook/canarying-releases/)

The verifier should distinguish a confirmed mismatch or violation from incomplete evidence. The deterministic controller can request a bounded repair for an actionable failure, await missing evidence, or escalate a deployment regression. Run candidate code in a least-privilege environment. Keep the release credential, contract policy, and independent checker outside the candidate’s writable scope. A PR that proposes changing verifier policy needs separate review, and any repository-level limitation on enforcing that independence remains a pilot limitation. [Codex sandbox settings](https://learn.chatgpt.com/docs/sandboxing) · [GitHub secure workflow guidance](https://docs.github.com/en/actions/reference/security/secure-use)

## What counts as an improvement

Use the [existing paired CLI eval](../evals/README.md) as the starting point. Change one variable per round. Hold the contract, test inputs, runner limits and verifier fixed across candidates. Gate promotion on identical or better correctness and required evidence, then compare elapsed time and token use. Record infra failures and count the attempts required to recover. Use held-out cases to test generalization before adopting a change broadly. Stop when two successive tested refinements miss the material-gain threshold. This tunes the delivery process without changing model weights.
